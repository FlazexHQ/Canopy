- **Fast paths:**
  - Direct replace: prechecks with constant filters evaluate on the replacement via `$unionWith` on the target collection, executing with `replaceOne` without a transaction (`crates/canopy-data/src/writes/plan.rs`).
  - Deferred read backs in atomic batches: read backs of documents that need no check and cannot be modified by later operations wait for the end of the transaction and run as one find per collection (`crates/canopy-data/tests/read_backs.rs`).
  - Grouped batches: consecutive single document writes of batches that are not atomic are grouped into an ordered client `bulkWrite` on MongoDB 8 and later (`WritePath.execute_each`).
  - Write sent with its idempotency record: a single insert or an update by `_id` with an idempotency key runs as one ordered client `bulkWrite` combining the write and its idempotency document inside the transaction (`crates/canopy-data/tests/record_with_write.rs`).
- **New route `document`:** `GET /rest/v1/{collection}/{id}` is selectable as `document` in `DataPlaneRoute`, reading a document by its `_id` through the read policy and field rules in a snapshot session (`ReadPath::find_by_id`); 22 recorded cases in `conformance/http/reads/cases/document.json` replay byte for byte on MongoDB 8 and 9.
- **TypeScript fixes found on the way:**
  - An update naming `_id` previously answered 500; it now correctly answers 400 (`6f79fc4`).
  - A keyed one operation batch kept an incorrect stored outcome when matching or changing nothing; the correction now properly updates results for batches (`c09eef7`).
- **Known differences, documented:**
  - A duplicate key refusal carries no `details.keyValue` for service callers in Rust because the Rust driver does not expose it.
  - Realtime mutations run in process skip the HTTP request rate limit that the forwarded `_batch` met; the engine's message rate limit continues to apply.
  - Each process keeps its own rate limit budget while routes are split between the gateway and TypeScript.
  - The gateway reads a `POST` body up to the limit before checking credentials (TypeScript checks credentials first).

### Task 4 Details (Stage D0: Batch Read Back Deferral and Fast Path Analysis)

- **Finding 7 (Partly Fixed for String and ObjectId IDs):** In an atomic batch of two or more operations (`WritePath.executeBatch`), read backs of written documents that need no check are queued (`ReadBacks` in `packages/rest/src/write-scope.ts`, new `readMany`, optional `defer` argument on `Scope.verify`, `Run` type now `(session, defer?)` in `packages/rest/src/write-plans.ts`) and read with one `find` per collection at the end of the transaction, before commit and before the idempotency document, still through `USING(read)` and read field rules evaluated by MongoDB.
- **Write Deferral Rules (`packages/rest/src/write-defer.ts`):** Decides which operations may defer: only when no later operation of the batch can touch the same document (a later `updateMany`/`deleteMany` or filter write on the collection, or the same `_id`, rules it out); only string and ObjectId ids (numeric ids are never deferred because Int32, Long, Double, and Decimal compare equal across types); string ids only when the collection has no default collation (looked up via `listCollections` before the transaction, cached 60 seconds per collection in `WritePath`; a failed lookup counts as collated). Operations with a real `check` filter keep the existing per operation `$facet` aggregate.
- **Command Counts:** In an atomic batch of 1 insert and 3 updates with string ids, command counts dropped from 9 to 7 (aggregate, insert, 3 updates, 1 find, commit). The D0 workload uses numeric `_id`s, so its "rest: atomic batch of 4" stays at 9 commands (remeasured by the orchestrator at 9.02 commands, unchanged).
- **Finding 3 (Analysis):** Replacing the fast path `updateOne` + `readOne` with a single `findOneAndUpdate` loses the modified count: `findAndModify` returns `{n, updatedExisting}` only, the same for a no op and a real change (checked on MongoDB 8.0.34). `modified` and `changedIds` come from `modifiedCount` today; REST responses carry `modified`, and `changedIds` feeds realtime echo waits. Decided on 2026-11-22 to keep 2 commands for exact `modified` counts.

### Task 5 Details (Stage D0: Replace Precheck, Grouped Batches, and Finding 4 Analysis)

- **Finding 5 (Done, Replace Without Transaction):** A single replace without a mutation ID or upsert evaluates `CHECK(update)` on the replacement through an aggregation on the target collection (`Scope.checkBefore`) and executes one `replaceOne` on the target filter with majority write concern, without a transaction (2 commands instead of 3). Falls back to the transaction path when: a mutation ID is supplied, an upsert is requested, the precheck fails or errors (the transaction then determines not found, conflict, `modified: 0`, or violation as before), the check reads `$$NOW` or other system variables besides `$$ROOT`/`$$CURRENT`/`$$REMOVE`, or the document size exceeds 8 MiB.
- **Finding 6 (Done, Grouped Non Atomic Batches):** Added `WritePath.executeEach` (public API, with `BatchItem`, `BatchItemResult`, and `WritePathOptions.groupBatches`, default `true`), used by the non atomic `_batch` route in `write-routes.ts`. On MongoDB 8.0+, consecutive single document inserts, updates by `_id` (whose check is implied), and replaces without mutation IDs targeting pairwise different documents are grouped into a single ordered client `bulkWrite` with `verboseResults`. Prechecks execute in a single aggregation per collection and operation kind (`precheckMany`) on the target collection, and read backs execute in one `find` per collection (`ReadBacks`). New helper `packages/rest/src/write-group.ts` (`GroupIds`) determines document identity conflicts conservatively. Operations rejected by MongoDB retry individually with their exact error, and subsequent writes form the next group; a replace whose precheck fails ends the group and executes alone.
- **Orchestrator Fix in Review:** A write concern error on a grouped `bulkWrite` without per write errors previously reported success for all members. Now every applied member receives the same error a standalone write receives (`Internal`, via `fromDriverError`), verified by a dedicated test in `packages/rest/test/write-each.test.ts`.
- **Finding 4 (Analysed, Retained at Two Commands):** Single round trip inserts via `$documents` + `$match` + `$merge` cannot achieve exact parity with the write path: a failed check cannot be distinguished from success without an additional round trip, `$merge` is rejected inside transactions (code 263), error parity for unique index and validator violations is not guaranteed, and `ct` as well as read back values differ. Insert remains at 2 commands.
